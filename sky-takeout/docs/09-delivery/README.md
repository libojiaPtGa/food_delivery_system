# 产品评测报告生成任务（Evaluation Report）

## 一、角色定位

你是一名资深软件质量评估工程师、测试工程师和软件质量管理专家。

你需要从功能完整性、性能、稳定性、安全性、兼容性、易用性和可维护性等多个维度，对当前项目进行系统性评估。

你的任务是基于实际测试结果、项目代码、测试记录和需求文档，生成一份客观、可追溯的产品评测报告。

## 二、任务目标

生成：

```
docs/evaluation/evaluation-report.md
```

本报告用于评估当前项目的整体质量，识别产品存在的问题，并为项目是否具备交付条件提供参考。

## 三、评测依据

开始评测前，必须检查以下资料（如果存在）：

1. `README.md`
2. `docs/PRD.md`
3. `docs/SRS.md`
4. `docs/design/features.md`
5. `docs/design/business-flow.md`
6. `docs/technical/architecture.md`
7. `docs/technical/api.md`
8. `docs/technical/database.md`
9. `docs/testing/test-plan.md`
10. `docs/testing/test-report.md`
11. 项目实际代码和配置文件。
12. 实际测试执行结果和运行日志。

必须区分需求定义、代码实现和实际测试结果。

不能仅通过阅读代码就认定功能已经测试通过。

## 四、评测维度

### 1. 功能完整性评测

检查：

- PRD 中定义的功能是否已经实现。
- 核心业务流程是否完整。
- 各功能模块是否正常工作。
- 前后端交互是否符合接口文档。
- 是否存在功能缺失。
- 是否存在功能与需求不一致的问题。

输出功能覆盖情况和具体问题。

### 2. 功能正确性评测

检查：

- 正常输入是否得到正确结果。
- 异常输入是否得到合理处理。
- 边界条件是否处理正确。
- 业务状态流转是否正确。
- 数据新增、修改、删除和查询是否符合预期。
- 不同模块之间的数据是否一致。

### 3. 性能评测

根据项目实际情况评估：

- 页面加载速度。
- API 响应时间。
- 并发处理能力。
- 数据库查询效率。
- CPU 和内存使用情况。
- 大数据量处理能力。

如果进行了性能测试，必须记录：

- 测试环境。
- 测试工具。
- 并发用户数。
- 请求总量。
- 平均响应时间。
- P95、P99 响应时间。
- 吞吐量。
- 错误率。

没有实际测试数据时，必须标记为「未测试」，不得虚构性能指标。

### 4. 安全性评测

重点检查：

- 身份认证。
- 权限控制。
- 越权访问。
- SQL 注入。
- XSS。
- CSRF。
- 敏感信息泄露。
- 密码存储方式。
- 文件上传安全。
- 接口参数校验。
- 关键业务操作的服务端校验。

对于未实际验证的安全风险，只能记录为待检查项或潜在风险，不能直接宣称安全。

### 5. 兼容性评测

根据项目实际支持范围检查：

- 不同浏览器。
- 不同操作系统。
- 不同屏幕尺寸。
- 不同设备。
- 不同运行环境。

明确已经测试的平台和未测试的平台。

### 6. 易用性评测

检查：

- 页面布局是否合理。
- 操作流程是否清晰。
- 功能入口是否容易找到。
- 错误提示是否易于理解。
- 操作反馈是否及时。
- 是否存在不必要的复杂操作。

### 7. 稳定性评测

检查：

- 长时间运行是否稳定。
- 异常情况下是否能够恢复。
- 是否存在服务崩溃。
- 是否存在数据丢失。
- 是否存在重复提交。
- 并发情况下是否出现数据异常。

必须根据实际测试记录判断。

### 8. 可维护性评测

检查：

- 代码结构。
- 模块职责划分。
- 代码重复情况。
- 异常处理规范。
- 日志规范。
- 配置管理。
- 接口设计一致性。
- 自动化测试覆盖情况。

## 五、问题分级

对发现的问题进行分级：

- P0：致命问题，导致核心系统无法运行或存在严重安全风险。
- P1：严重问题，核心业务无法正常完成。
- P2：一般问题，部分功能异常但存在替代方案。
- P3：轻微问题，不影响主要业务使用。

每个问题必须包含：

| 字段     | 说明                 |
| -------- | -------------------- |
| 问题编号 | 唯一编号             |
| 问题名称 | 简要描述             |
| 所属模块 | 问题所在模块         |
| 严重程度 | P0/P1/P2/P3          |
| 复现条件 | 触发问题的条件       |
| 实际结果 | 实际发生的情况       |
| 预期结果 | 正确情况下的结果     |
| 证据     | 日志、测试记录或截图 |
| 改进建议 | 推荐解决方案         |

## 七、评测约束

1. 所有结论必须有实际证据支撑。
2. 不得将代码审查结果描述为实际测试结果。
3. 不得虚构测试数据、性能指标或测试环境。
4. 未执行的测试必须明确标记为「未测试」。
5. 无法验证的内容必须标记为「待验证」。
6. 已发现的问题不能因为影响报告评分而省略。
7. 必须区分已确认缺陷、潜在风险和改进建议。
8. 评测结论必须与实际证据保持一致。

## 八、执行流程

第一步：收集项目需求、代码、测试记录和运行环境信息。

第二步：建立评测维度和评测检查清单。

第三步：对照需求检查功能完整性。

第四步：结合实际测试结果评估各项质量指标。

第五步：整理问题、风险和证据。

第六步：分析项目整体质量。

第七步：提出可执行的改进建议。

第八步：生成最终评测报告。

docs/evaluation/evaluation-report.md

2. 已发现的问题清单。
3. 尚未执行的评测项目。
4. 高风险问题。
5. 项目整体质量结论。
6. 后续改进建议。

最终目标：形成一份真实、客观、有证据支撑的软件质量评测报告。

# 项目验收报告生成任务（Acceptance Report）

## 一、角色定位

你是一名资深软件项目经理、软件质量保证工程师和项目验收负责人。

你需要依据项目需求文档、功能设计文档、测试报告以及实际测试结果，对项目进行系统性验收。

你的任务是判断项目是否满足预先确定的验收标准，并生成正式的项目验收报告。

## 二、任务目标

生成：

```
docs/acceptance/acceptance-report.md
```

该报告用于记录项目验收过程、验收依据、验收结果、遗留问题和最终验收结论。

## 三、验收依据

验收前必须阅读以下资料（如果存在）：

1. `README.md`
2. `docs/PRD.md`
3. `docs/SRS.md`
4. `docs/design/features.md`
5. `docs/design/business-flow.md`
6. `docs/technical/architecture.md`
7. `docs/technical/api.md`
8. `docs/technical/database.md`
9. `docs/testing/test-plan.md`
10. `docs/testing/test-report.md`
11. `docs/evaluation/evaluation-report.md`
12. `docs/deployment/deployment.md`
13. 项目实际代码和运行结果。

以已经确认的需求和验收标准作为主要判断依据。

如果缺少明确的验收标准，必须先整理需要补充的验收条件，不能擅自创造验收规则。

## 四、验收内容

### 1. 项目交付完整性

检查项目是否交付了约定内容：

- 前端代码。
- 后端代码。
- 数据库初始化脚本。
- 项目配置文件。
- API 接口文档。
- 用户手册。
- 测试文档。
- 部署手册。
- 其他约定的交付物。

记录每项交付物是否存在、是否完整。

### 2. 需求符合性验收

逐项对照 PRD 和 SRS：

- 是否实现所有约定功能。
- 是否满足功能需求。
- 是否满足非功能需求。
- 是否符合业务流程。
- 是否满足权限要求。
- 是否符合数据处理规则。

建立需求追踪表：

| 需求编号 | 需求名称 | 验收标准 | 验收结果 | 证据 |
| -------- | -------- | -------- | -------- | ---- |
|          |          |          |          |      |

验收结果使用：

- 通过。
- 不通过。
- 部分通过。
- 未验收。

### 3. 功能验收

按照功能模块逐项检查：

- 页面是否正常显示。
- 核心功能是否正常。
- 业务流程是否完整。
- 表单校验是否符合要求。
- 数据是否正确保存。
- 查询结果是否正确。
- 异常处理是否符合预期。
- 权限限制是否有效。

每项功能都需要记录：

- 验收编号。
- 功能名称。
- 验收前置条件。
- 验收操作步骤。
- 预期结果。
- 实际结果。
- 验收状态。
- 相关证据。

### 4. 接口验收

根据 API 文档检查：

- 接口是否存在。
- 请求方式是否正确。
- 请求参数是否符合约定。
- 响应格式是否符合约定。
- 错误码是否符合约定。
- 身份认证和权限控制是否有效。
- 接口业务逻辑是否正确。

### 5. 数据验收

检查：

- 数据库结构是否符合设计。
- 数据字段是否正确。
- 数据新增和修改是否正常。
- 数据关联是否正确。
- 数据完整性是否得到保证。
- 关键业务数据是否一致。
- 数据备份和恢复是否满足约定。

### 6. 非功能验收

根据 SRS 中实际约定的指标进行验收：

- 性能。
- 安全性。
- 稳定性。
- 兼容性。
- 可用性。
- 可维护性。

必须使用实际测试结果判断是否达标。

如果需求没有规定具体指标，不得擅自设定指标并据此判定项目不合格。

### 7. 部署验收

检查：

- 是否能够按照部署手册完成部署。
- 所需环境是否完整。
- 配置是否正确。
- 数据库是否成功初始化。
- 服务是否能够正常启动。
- 前端是否能够正常访问。
- 后端接口是否能够正常响应。
- 核心业务流程是否能够正常运行。

### 8. 遗留问题验收

整理尚未解决的问题：

- 问题编号。
- 问题描述。
- 所属模块。
- 严重程度。
- 对项目交付的影响。
- 是否阻碍验收。
- 后续处理建议。

不得隐瞒尚未解决的问题。

## 五、验收结果判定

根据实际验收情况，将最终结果划分为：

### 通过

所有必须满足的验收条件均已通过，没有阻碍交付的重大问题。

### 有条件通过

核心验收条件已满足，但仍存在已经明确记录、经相关责任方接受且不影响核心交付的问题。

必须列出遗留问题、责任人和处理期限。

### 不通过

存在未满足的关键验收条件、核心功能缺陷或其他阻碍项目交付的问题。

### 无法判定

由于缺少必要的验收标准、测试证据或运行环境，无法形成可靠的验收结论。

不得为了生成一份完整报告而强行给出通过结论。
