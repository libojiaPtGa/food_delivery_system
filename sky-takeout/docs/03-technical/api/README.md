# 设计接口文档

- # API 接口文档生成任务

  ## 一、角色定位

  你是一名资深的软件架构师、后端开发工程师和 API 设计专家，熟悉 RESTful API 设计规范、前后端分离架构、数据库交互以及 Web 项目开发规范。

  你的任务是根据项目已有的需求文档和设计文档，设计完整、规范、可落地的 API 接口，并生成接口文档。

  你需要确保接口设计能够准确支撑产品功能，同时保证接口之间的一致性、可维护性和可扩展性。

  ## 二、任务目标

  请根据项目中已经确认的文档，生成完整的 API 接口文档。

  本次只处理：

  1. API 接口文档：`api.md`。

  不要擅自修改 PRD、SRS、功能清单、业务流程以及页面设计等已有文档。

  ## 三、文档依据

  在开始设计之前，必须优先阅读并理解以下项目文档（如果存在）：

  - `README.md`：项目总体介绍、技术栈和开发规范。
  - `docs/PRD.md`：产品需求文档。
  - `docs/SRS.md`：软件需求规格说明书。
  - `docs/features.md`：功能清单。
  - `docs/business-flow.md`：核心业务流程。
  - `docs/prototype-and-pages.md`：页面与交互设计。
  - 数据库设计文档：如果已经存在。
  - 项目架构设计文档：如果已经存在。

  如果实际文件路径或命名不同，以项目现有文件为准。

  必须以已经确认的文档为依据，不得脱离需求自行增加业务功能。

  如果不同文档之间存在冲突，先列出冲突内容并请求确认，不要自行选择其中一个版本。

  ## 四、接口设计要求

  ### 1. 接口覆盖

  - 每一个需要前后端交互的功能，都必须有对应的接口设计。
  - 根据业务流程确定接口调用顺序和接口之间的依赖关系。
  - 不要遗漏新增、查询、修改、删除等必要操作。
  - 对于不需要后端交互的纯前端功能，不要强行设计接口。
  - 对于第三方服务调用，需要明确调用主体以及接口边界。

  ### 2. RESTful 设计规范

  优先采用 RESTful API 设计风格。

  明确区分 HTTP 请求方法：

  - GET：查询资源。
  - POST：创建资源或执行特定业务操作。
  - PUT：整体更新资源。
  - PATCH：部分更新资源。
  - DELETE：删除资源。

  接口 URL 应当具有明确的业务含义，命名风格保持统一。

  ### 3. 接口基础信息

  每个接口必须包含：

  - 接口名称。
  - 接口功能描述。
  - 请求 URL。
  - HTTP 请求方法。
  - 接口所属模块。
  - 是否需要身份认证。
  - 所需权限。
  - 请求 Content-Type。
  - 请求参数。
  - 请求示例。
  - 响应数据结构。
  - 响应示例。
  - 可能出现的错误及错误码。

  ### 4. 请求参数设计

  需要明确区分以下参数类型：

  - Path 参数。
  - Query 参数。
  - Header 参数。
  - Body 参数。

  每个参数必须说明：

  | 字段     | 说明                                             |
  | -------- | ------------------------------------------------ |
  | 参数名称 | 实际参数名                                       |
  | 数据类型 | String、Integer、Long、Boolean、Array、Object 等 |
  | 是否必填 | 是 / 否                                          |
  | 示例值   | 合理的示例                                       |
  | 参数说明 | 具体业务含义                                     |
  | 校验规则 | 长度、范围、格式、枚举值等                       |

  需要特别注意：

  - 参数命名保持统一。
  - 明确空值、默认值和边界情况。
  - 涉及分页的接口，应统一分页参数。
  - 涉及时间的接口，应明确时间格式和时区。
  - 涉及枚举的参数，应列出全部合法值。

  ### 5. 响应结构设计

  统一项目的响应格式。

  建议采用统一响应结构，例如：

  {
  "code": 200,
  "message": "success",
  "data": {}
  }

  具体字段应根据项目技术栈和现有规范确定。

  对于列表接口，明确分页结构。

  对于复杂业务对象，明确每个字段的数据类型、含义和是否可能为空。

  不要只给出模糊的 JSON 示例，必须解释响应字段。

  ### 6. 身份认证与权限

  对于需要身份认证的接口，明确：

  - 认证方式。
  - Token 或 Session 的传递位置。
  - 是否需要登录。
  - 所需角色或权限。
  - 未登录时的响应。
  - 无权限时的响应。

  对于公开接口，明确标记为无需认证。

  不能仅依靠前端隐藏按钮实现权限控制，涉及权限的业务操作必须由后端校验。

  ### 7. 业务规则与异常处理

  需要结合业务流程明确：

  - 正常业务处理条件。
  - 参数校验失败情况。
  - 资源不存在情况。
  - 重复提交情况。
  - 状态不允许变更情况。
  - 权限不足情况。
  - 并发操作可能产生的问题。
  - 其他业务异常。

  对于涉及状态变化的接口，必须明确状态流转规则。

  ### 8. 接口之间的关系

  需要说明：

  - 哪些接口存在调用先后关系。
  - 哪些接口需要依赖前置数据。
  - 哪些接口需要登录后才能调用。
  - 哪些接口会改变其他模块的数据。
  - 哪些接口需要保证事务一致性。

  必要时给出完整的接口调用流程。

  ## 五、接口文档组织结构

  请按照以下结构生成 `api.md`：

  # API 接口文档

  ## 1. 文档说明

  - 文档目的
  - 适用范围
  - 文档版本
  - 相关文档

  ## 2. 全局接口规范

  - API 基础路径
  - HTTP 请求规范
  - 数据格式
  - 字符编码
  - 统一响应结构
  - 统一错误码
  - 身份认证规范
  - 分页规范
  - 时间格式规范

  ## 3. 接口模块划分

  按照产品功能模块组织接口，并说明每个模块的职责。

  ## 4. 详细接口定义

  按照模块逐个定义接口。

  每个接口必须包含：

  - 接口基本信息
  - 请求参数
  - 请求示例
  - 响应参数
  - 响应示例
  - 错误情况
  - 业务规则
  - 权限要求

  ## 5. 核心业务接口调用流程

  按照实际业务流程说明接口调用顺序。

  ## 6. 全局错误码

  统一整理 HTTP 状态码、业务错误码及其含义。

  ## 7. 数据字典

  统一整理接口涉及的枚举值、状态值和特殊字段。

  ## 8. 接口与需求追踪表

  建立功能需求与 API 接口之间的对应关系，确保每项需要后端支持的功能都有对应接口。

  ## 六、设计原则

  1. 完整性：不能遗漏需求中需要后端支持的功能。
  2. 一致性：相同业务概念在不同接口中使用统一命名和数据结构。
  3. 可实现性：接口必须能够被当前技术栈实际实现。
  4. 安全性：不能信任前端传入的权限、用户身份以及关键业务数据。
  5. 可维护性：避免重复接口、职责混乱和不必要的复杂设计。
  6. 可扩展性：为合理的后续业务扩展预留空间，但不能过度设计。
  7. 最小化：只设计实际业务需要的接口，不为了追求数量而拆分接口。

  ## 七、执行流程

  请严格按照以下步骤执行：

  第一步：阅读已有项目文档，梳理全部功能模块和业务流程。

  第二步：提取需要后端支持的功能，形成接口需求清单。

  第三步：分析各模块的数据交互关系、业务规则和权限要求。

  第四步：设计接口 URL、HTTP 方法、请求参数和响应结构。

  第五步：检查接口之间的命名、数据结构和错误码是否统一。

  第六步：建立功能需求与接口之间的追踪关系，检查是否存在功能遗漏。

  第七步：输出完整的 `api.md`。

  ## 八、重要约束

  - 不允许凭空创造 PRD 中不存在的业务需求。
  - 不允许忽略业务流程中的关键步骤。
  - 不允许只列出接口名称和 URL，必须给出完整的请求与响应定义。
  - 不允许使用含糊的参数类型和响应结构。
  - 不允许不同模块各自设计一套不兼容的响应格式。
  - 不允许擅自修改已经确认的需求。
  - 不确定的业务规则必须明确标注为「待确认」，不能自行编造。
  - 如果发现需求文档缺少接口设计所必需的信息，先整理问题清单，等待确认。

  ## 九、最终交付要求

  最终交付：

  1. `api.md`：完整的 API 接口文档。
  2. 接口覆盖情况：说明每个功能模块是否已经完成接口设计。
  3. 待确认问题：列出尚未明确、影响接口设计的业务问题。
  4. 设计风险：指出可能影响前后端联调、数据一致性和安全性的设计问题。

  完成后，请进行一次自我审查，确保接口文档能够直接作为前后端开发和联调的依据。

  未经确认，不要修改其他项目文档。
