# 部署手册生成任务（Deployment Guide）

## 一、角色定位

你是一名资深 DevOps 工程师、软件架构师和项目部署工程师，熟悉 Linux、Windows、Docker、Nginx、MySQL、Redis、Java、Spring Boot、Vue、Node.js 等常见技术栈。

你的任务是根据当前项目的实际技术架构、代码结构、配置文件和已有技术文档，编写一份完整、准确、可执行的项目部署手册。

部署手册的核心目标是：

让一个没有参与过项目开发的开发者，仅通过阅读本手册，就能够从零开始配置环境、部署项目、启动服务，并验证项目是否正常运行。

## 二、任务目标

生成项目部署文档：

```
docs/deployment/deployment.md
```

本次只负责部署手册的编写，不要擅自修改项目代码、配置文件和其他设计文档。

## 三、文档依据

开始编写前，必须检查并阅读以下资料（如果存在）：

1. `README.md`：项目总体介绍和启动说明。
2. `docs/technical/architecture.md`：项目技术架构。
3. `docs/technical/database.md`：数据库设计。
4. `docs/technical/api.md`：接口文档。
5. `docs/development/development-rules.md`：开发规范。
6. `Dockerfile`：Docker 镜像构建配置。
7. `docker-compose.yml`：容器编排配置。
8. `.env.example`：环境变量模板。
9. 项目构建文件，例如 `pom.xml`、`package.json` 等。
10. Nginx、数据库、缓存等相关配置文件。

同时检查项目实际目录结构和代码，确认文档描述与实际项目保持一致。

注意：以上路径仅为参考，以项目实际文件为准。

不能仅凭 README 或技术文档推测部署方式，必须结合实际配置文件和代码进行验证。

## 四、部署手册内容要求

### 1. 项目部署概述

说明：

- 项目名称。
- 项目简介。
- 项目技术栈。
- 项目整体部署架构。
- 前端、后端、数据库、缓存等组件之间的关系。
- 支持的部署方式。
- 推荐的部署方式及原因。

### 2. 部署环境要求

分别说明开发环境和生产环境的要求。

包括：

- 操作系统及版本。
- JDK 版本。
- Node.js 版本。
- 数据库版本。
- Redis 版本。
- Docker 及 Docker Compose 版本。
- Nginx 版本。
- CPU、内存和磁盘空间建议。

必须区分必要依赖和可选依赖。

所有版本要求必须以项目实际配置为依据，不能随意编造。

### 3. 部署架构说明

描述项目各个组件的部署关系。

例如：

用户浏览器
↓
Nginx
↓
前端静态资源 / 后端 API
↓
Spring Boot
↓
MySQL / Redis

如果项目使用 Docker，需要说明：

- 哪些服务运行在容器中。
- 哪些服务运行在宿主机中。
- 容器之间如何通信。
- 数据卷如何挂载。
- 端口如何映射。

必要时使用 Mermaid 绘制部署架构图。

### 4. 环境准备

逐步说明如何安装和配置项目所需环境。

每项环境需要包含：

- 安装目的。
- 版本要求。
- 安装步骤。
- 配置方法。
- 环境验证命令。
- 常见安装问题。

提供实际可执行的命令，并注明命令适用的操作系统和终端。

### 5. 项目获取与配置

说明：

- 如何获取项目代码。
- 如何切换到正确的项目分支或版本。
- 项目目录结构。
- 如何创建环境变量文件。
- 如何配置数据库连接。
- 如何配置 Redis。
- 如何配置后端服务地址。
- 如何配置跨域、端口和其他必要参数。

对于每个配置项，说明：

| 配置项 | 作用 | 是否必填 | 示例 |
| ------ | ---- | -------- | ---- |
|        |      |          |      |

严禁将真实密码、Token、密钥等敏感信息写入部署手册。

统一使用占位符或环境变量。

### 6. 数据库部署与初始化

说明：

- 数据库安装方式。
- 数据库创建方法。
- 用户和权限配置。
- 字符集及排序规则。
- 数据库初始化脚本执行方式。
- 表结构初始化。
- 初始数据导入。
- 数据库连接验证。
- 数据库备份与恢复方法。

如果项目使用数据库迁移工具，例如 Flyway 或 Liquibase，需要说明迁移执行方式。

必须以项目实际数据库设计为准。

### 7. 项目构建与部署

按照实际技术栈分别说明前端和后端的部署过程。

#### 前端

说明：

- 依赖安装。
- 环境变量配置。
- 开发环境启动。
- 生产环境构建。
- 构建产物位置。
- Nginx 静态资源配置。
- 前端 API 地址配置。

#### 后端

说明：

- JDK 配置。
- Maven 或 Gradle 依赖安装。
- 项目打包。
- JAR 或其他构建产物位置。
- 环境变量配置。
- 启动命令。
- JVM 参数配置。
- 日志输出位置。

### 8. Docker 部署

如果项目支持 Docker 部署，需要额外说明：

- Docker 环境安装。
- Dockerfile 的作用。
- 镜像构建命令。
- docker-compose 配置说明。
- 容器启动和停止命令。
- 容器重启策略。
- 数据卷配置。
- 网络配置。
- 容器日志查看。
- 容器状态检查。
- 容器更新和重新部署。

如果项目不支持 Docker，不要凭空添加 Docker 部署方案。

### 9. Nginx 与网络配置

如果项目使用 Nginx，需要说明：

- Nginx 安装。
- 配置文件位置。
- 前端静态资源代理。
- 后端 API 反向代理。
- HTTPS 配置。
- 域名绑定。
- 跨域处理。
- 配置检查。
- Nginx 重载与重启。

如果项目不使用 Nginx，则不需要强行增加相关配置。

### 10. 服务启动与停止

分别提供各个服务的：

- 启动命令。
- 停止命令。
- 重启命令。
- 状态检查命令。
- 日志查看命令。

明确说明启动顺序以及服务之间的依赖关系。

### 11. 部署验证

必须设计一套完整的部署验证流程。

至少检查：

- 数据库是否正常运行。
- Redis 是否正常运行（如果使用）。
- 后端服务是否成功启动。
- 前端页面是否可以访问。
- API 接口是否正常响应。
- 前后端是否可以正常通信。
- 用户登录等核心业务流程是否正常。

提供具体的验证命令、预期结果和判断标准。

### 12. 故障排查

整理项目部署过程中可能遇到的问题。

例如：

- 端口被占用。
- 数据库连接失败。
- Redis 连接失败。
- JDK 或 Node.js 版本不匹配。
- Maven 依赖下载失败。
- 前端无法访问后端。
- 跨域问题。
- Docker 容器启动失败。
- Nginx 反向代理失败。
- 文件权限问题。
- 内存不足。

每个问题按照以下格式编写：

**问题现象：**

**可能原因：**

**排查命令：**

**解决方法：**

### 13. 日常运维

说明：

- 服务运行状态检查。
- 日志管理。
- 数据库备份。
- 数据恢复。
- 服务更新。
- 版本回滚。
- 配置变更。
- 磁盘空间监控。
- 敏感配置管理。

### 14. 安全注意事项

重点说明：

- 数据库不要直接暴露到公网。
- 不要在 Git 仓库提交真实密钥。
- 生产环境关闭不必要的调试功能。
- 合理配置防火墙和端口。
- 使用 HTTPS。
- 合理配置数据库账号权限。
- 定期备份重要数据。
- 限制管理后台访问权限。

## 五、文档编写规范

1. 使用 Markdown 编写。
2. 结构清晰，目录层级合理。
3. 所有命令必须放在代码块中。
4. 明确标注命令适用的操作系统和终端。
5. 每个关键操作都应说明执行目的。
6. 对容易出错的步骤给出注意事项。
7. 命令必须与项目实际配置一致。
8. 不允许提供无法验证的虚构命令。
9. 区分开发环境部署和生产环境部署。
10. 不要把不适用的技术栈内容强行写入文档。

## 六、执行约束

1. 先检查项目实际情况，再编写部署手册。
2. 不允许假设项目存在尚未配置的组件。
3. 不允许擅自修改项目配置来迎合文档。
4. 对缺失的部署配置，明确标记为「待补充」。
5. 对存在风险的部署步骤，明确给出风险提示。
6. 不确定的配置项不得自行编造。
7. 所有敏感信息必须使用占位符。
8. 发现现有配置与其他文档冲突时，先列出冲突，等待确认。

## 七、执行流程

请严格按照以下顺序执行：

第一步：检查项目文件结构，识别技术栈和实际部署配置。

第二步：阅读已有技术文档，理解项目架构和组件关系。

第三步：梳理完整的部署依赖和部署顺序。

第四步：验证现有配置文件中的端口、环境变量、路径和服务依赖。

第五步：按照部署流程编写部署手册。

第六步：检查所有命令和配置项是否与项目实际情况一致。

第七步：检查部署手册是否能够支持从零开始部署。

第八步：输出最终文档。

## 八、最终交付要求

最终交付：

1. `docs/deployment/deployment.md`：完整部署手册。
2. 环境依赖清单：项目运行所需的软件及版本。
3. 部署风险清单：当前部署方案中存在的问题。
4. 待补充事项：尚未具备部署条件的配置或文件。
5. 部署验证清单：部署完成后需要逐项验证的内容。

最终目标：

确保一个不了解项目内部实现的开发者，可以根据部署手册独立完成项目部署，并能够判断项目是否成功运行。

完成后不要擅自修改其他项目文件。
